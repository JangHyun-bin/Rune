# v1.0.1 Native Menu Bar & Tab-Drag-to-Split QA

Two additions this cycle: a native File/View/Help menu bar (with native-window-theme
sync and a toolbar alignment fix), and dragging an already-open tab onto a pane edge
or a different pane's center (VSCode-style split/move). Both shipped with no feature
flag — unlike `VITE_NATIVE_DOCKING`, they are always on.

This doc records what was actually exercised versus what was only verified by
reading code against the real crate/library source. An item never becomes "pass"
from a code review alone, matching the standard set by
`v1.0.1-native-docking.md`.

## Tab drag to pane split/move

Mouse-event-based (not HTML5 drag-and-drop): Windows requires
`dragDropEnabled:false` in `tauri.conf.json` for HTML5 `dragstart`/`dragover`/`drop`
to fire at all, and this app can't set that without breaking OS file drag-in
(`fileDrop.ts`'s `handleNativeFileDrop`, which depends on Tauri's native drag-drop
event). `mousedown`/`mousemove`/`mouseup` with a movement threshold sidesteps this
entirely and reuses the same drop-zone hit-testing and overlay as native file drag-in.

| Item | Status | Evidence |
|---|---:|---|
| Drag a tab onto a pane edge → splits with that file | pass | confirmed live in the hosted Windows dev build after the mouse-event rewrite |
| Drop-zone overlay animates smoothly between zones instead of snapping | pass | CSS transition added and confirmed live |
| Drag a tab onto a different pane's center → moves it there | unverified | not exercised |
| Ctrl/Cmd-drag keeps the source tab open (duplicate) instead of closing it | unverified | not exercised |
| Untitled/unsaved tab (no path) produces no drop target | unverified interactively — matches design (`handleInternalTabDrop` returns `false` when `payload.path` is null) and is covered by a unit test, but never dragged by hand |
| OS file drag-in (Explorer → app) still works after this change | unverified | code path untouched by this fix, but not re-confirmed interactively after switching the tab-drag mechanism |
| 3+ pane scenarios | unverified | only a 2-pane split was exercised |

## Platform coverage this cycle

Everything above was exercised (or explicitly left unverified) on **Windows only** —
no macOS or Linux machine was available. Both features are release-candidate
material specifically because of this gap: `1.0.1-rc.1` ships with the
code-reviewed-only and unverified rows above still open, to be closed out by real
usage before promoting to `1.0.1` final.
