# v1.0.1 Native Cross-window Docking Gate

Task 1 established Rune's native drag boundary. Tasks 5–8 gate the complete View transaction: actual-pointer tear-off, restored detached-window drag, exact-target re-dock, persistence, and restart recovery. The **Move to New Window** menu item and detached `↙` button remain fallbacks and are never used for the primary cross-window assertion.

## Acceptance gate

The gate passes only if each supported OS can start a native window drag, reconcile CSS client coordinates with Tauri physical screen coordinates, move Outline into the requested Panel group, keep the dirty editor sentinel unchanged, reduce the native window count from two to one, and preserve the exact destination through another restart.

| OS | OS pointer boundary | tear-off | exact Panel re-dock | restart persistence | evidence |
|---|---:|---:|---:|---:|---|
| Windows | pass | pass | pass | pass | hosted actual-pointer run `31480247908` |
| macOS | pass | pass | pass | pass | hosted actual-pointer run `31480247908` |
| Linux | pass | unverified | unverified | deterministic only | boundary run `31473710553`; manual desktop gate required |

The table may be promoted to complete only from an actual operating-system pointer run. PointerEvents dispatched by WebDriver or Vitest never satisfy these columns.

## Deterministic transaction coverage

The regular Vitest matrix runs on Windows, macOS, and Linux and covers protocol-v2 normalization, duplicate sessions, Escape and invalid-drop cancellation, transport failure, negative acknowledgement, timeout rollback, source/target loss, commit-once behavior, exact serialized-layout preservation, and version-1 migration/recovery. These tests use scripted adapters and are reported as deterministic transport evidence, not actual-pointer evidence.

The Windows and macOS native three-session E2E sequence performs:

1. Actual pointer drag-out of Outline, exact serialization comparison after Escape, and detached-layout save.
2. Restart and restore of that detached View, actual pointer drag to the requested Panel group, native window count `2 → 1`, exact `containerId`/group/order assertions, dirty-editor preservation, and save.
3. Another restart and verification that the requested Panel destination and dirty editor survived.

Linux uses the same deterministic protocol, migration, rollback, and restart fixtures, and its hosted runner executes the actual OS pointer boundary. The complete detached-to-Panel pointer scenario remains manual because Xvfb/Openbox plus `tauri-driver` reparents the detached WebKit input window separately from its native frame after `startDragging()`. The DOM and X11 frame then expose different screen origins, so the hosted gesture cannot reach the visible tab reliably. Test-only layout offsets or scripted PointerEvents are not accepted as substitutes.

Scale conversion fixtures cover `1`, `1.25`, `1.5`, and `2`, including negative monitor origins. Runner-native scale factors and monitor topology are recorded separately; unavailable physical monitor combinations remain explicit manual-matrix items rather than simulated passes.

## Actual-pointer implementation

WebDriver locates sources and destinations and reads committed state. Windows `user32`, macOS CoreGraphics, and Linux `xdotool` supply actual OS input because browser-synthesized pointer actions do not move the OS cursor. The Windows and macOS gates record the complete gesture, destination snapshot, window counts, and restart state. Hosted Linux currently records only the native pointer/movement boundary; a normal Linux desktop must supply the complete destination evidence.

The helper installs no global mouse hook. Rune treats `startDragging()` as an initiation request, not a completion signal: movement observations plus a stable idle interval define the native drop boundary. Active-drag geometry is not persisted, so a cancelled or rejected transaction retains byte-for-byte serialized layout state.

## Evidence history

The earlier boundary-only three-OS evidence is GitHub Actions run [31374022010](https://github.com/JangHyun-bin/Rune/actions/runs/31374022010). The current three-OS boundary workflow is [31473710553](https://github.com/JangHyun-bin/Rune/actions/runs/31473710553). These prove native movement and coordinate conversion but must not be described as cross-window docking validation.

Hosted Windows and macOS completed the actual-pointer tear-off, exact Panel re-dock, dirty-buffer, and restart sequence in [31480247908](https://github.com/JangHyun-bin/Rune/actions/runs/31480247908). The run is intentionally not cited as a three-OS pass: its Linux job exposed the Xvfb/Openbox `tauri-driver` reparenting limitation described above.

Local Windows Task 8 evidence used a real pointer at 150% scale and passed tear-off, restored detached-to-Panel docking, exact group/order assertions, dirty-editor preservation, window-count closure, and second-restart persistence.

Until a normal Linux desktop records the missing result, `VITE_NATIVE_DOCKING=1` remains required and the legacy HTML5 Workbench View drag path remains available. The release workflow continues to require the complete Linux scenario, so the limitation cannot silently promote a release.
