# v1.0.1 Native Docking Feasibility

Task 1 validates only Rune's native drag boundary. It does not implement a docking transaction.

## Acceptance gate

The gate passes only if each supported OS can start a native window drag, observe native move events, reconcile CSS client coordinates with Tauri physical screen coordinates, and detect a stable post-drag window position without a global input hook.

| OS | startDragging resolves after release | onMoved during drag | cursor is physical | mixed-DPI conversion | result |
|---|---:|---:|---:|---:|---|
| Windows | no | yes | yes | pass | pass |
| macOS | no | yes | yes | pass | pass |
| Linux | yes | yes | yes | pass | pass |

## Automated probe

The `native-drag-boundary` workflow performs a real operating-system pointer press, move, and release against a Tauri-only drag handle. WebDriver arms the probe and reads the result; platform input APIs supply the native gesture because browser-synthesized pointer actions do not move the OS cursor. The probe records the native window origin, scale factor, cursor position, `onMoved` events, `startDragging()` timing, and post-release position stability. A fractional 1.5x/negative-origin fixture verifies the mixed-DPI conversion on every runner; the runner's actual scale factor is retained in the evidence log.

This probe does not install an operating-system mouse hook and does not request macOS Accessibility permission. The passing three-OS evidence is GitHub Actions run [31374022010](https://github.com/JangHyun-bin/Rune/actions/runs/31374022010).

## Windows observation

Local Windows validation used a 150% scale factor. `cursorPosition()` matched the physical screen coordinate derived from the WebView client point exactly within floating-point precision, 58 `onMoved` events were observed, and two post-release native-origin samples 250 ms apart were identical. `startDragging()` resolved about 1.31 seconds before `mouseup`, so Rune must not treat that Promise as drag completion; movement quiescence and stable native bounds provide the completion boundary without a global input hook.

The Windows CI runner independently reported exact `(176, 115)` cursor reconciliation, one native move event, a `(180, 120)` window displacement, and identical post-drag origin samples.

## macOS observation

The macOS 15 runner exposed a platform-specific boundary: Tauri's `innerPosition()` returned `(0, 25)`, but the DOM client origin was `(0, 53)` because WKWebView applied a 28-point top safe-area inset. The minimal `native_webview_origin` command reads the actual WKWebView screen rect and its AppKit safe-area insets, then converts them into the same CoreGraphics physical coordinate space as `cursorPosition()`. The corrected cursor and converted client coordinate both measured `(168, 137)`. Six `onMoved` events were observed, the window moved to `(139, 55)`, and the two post-drag samples were identical. `startDragging()` resolved before release, so macOS also requires movement quiescence and stable bounds for completion.

## Linux observation

The Ubuntu 24.04 Xvfb runner reported scale factor 1. The cursor and converted client coordinate were both `(168, 84)`, 12 `onMoved` events were observed, the window moved by `(180, 120)`, and post-release native-origin samples were identical. On this runner `startDragging()` resolved after release. Rune still uses the cross-platform movement-quiescence and stable-bounds boundary rather than relying on this OS-specific Promise timing.
